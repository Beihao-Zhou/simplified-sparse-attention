# 0001 长 agent 轨迹的推理与两阶段训练 infra

状态：已接受（2026-11-21）。相关 issue：#10（1M decode 的 kernel 设计）、#11（深层树、decode 时的 gist 与 1M）、#14（深层树的逐级误差累积）、#15（32K 以上的位置与老师路线）。

## 背景

这份 ADR 回答一个问题：要让这套代码支持长 agent 轨迹的推理和两阶段训练（阶段一 gist 压缩、阶段二 OPSD），中间每个结构性的选择取什么。下文用到 SSA 的术语：每 4 个原始 token 插一个 gist，每 4 个 gist 插一个 meta-gist，更高的层级依此类推，统称 summary；decode 时逐级从 summary 里选出要展开的块，称为 selective unfolding。

agent 轨迹和现有的长文本评测有三处不同，下面的决定都由这三处推出。第一，轨迹是一轮一轮追加出来的：每轮先追加一段工具返回的结果（1K–50K token），再生成几百到一千 token。第二，轨迹有结构：开头是 system prompt 和工具定义，之后 assistant 的输出和工具结果交替出现。第三，公开轨迹的长度几乎都在 128K 以内（CoderForge 的中位数 38K、P99 91K），没有接近 1M 的数据。

决定于 2026-11-21 的一次逐项讨论中定下，每条都写明选了什么、没选什么、为什么。推翻其中任何一条都需要实验数据。

## 目标与范围

**结构按 1M 设计，质量目标定在 256K，先在 128K 上跑通。** Qwen2.5-7B-Instruct-1M 只训练到 256K，256K 以上靠 dual chunk attention（DCA）加 YaRN 外推；HF transformers 没有 DCA，模型卡写明超过 262,144 个 token 可能掉精度，上游 vLLM 也已删除 DCA。256K 以内老师和学生的位置编码都在训练范围内，质量对比才干净。在我们的补丁里实现 DCA 没有选：它要求每次 attention 按三种相对位置分开计算，并和 gist 的位置规则对齐，会把位置编码问题和压缩、路由问题混在一起。DCA，以及"只给远处的 summary 做位置重映射"的想法，另开 issue。

**主线模型是 Qwen2.5-7B-Instruct-1M，纵向链路和快速 spike 用 Qwen2.5-0.5B-Instruct。** 7B-1M 是 Qwen2 架构，现有模型补丁可以直接用；它的形状（28 层、28 个 query head、4 个 KV head、head dim 128）和现有 kernel 一致。1M 版本只有 7B 和 14B。0.5B 的迭代速度快一个数量级以上，已有的 spike 代码和 checkpoint 都能复用。模型补丁不和某个模型绑定，以后换成 agent 能力更强的模型只需再写一个补丁。

**开发时看 KL，里程碑看任务成功率。** 开发指标是留出轨迹上每一轮 assistant 输出与全注意力老师的平均 token KL，几分钟就能测一次；agent 任务成功率又慢又噪声大，只在里程碑跑。

## 压缩规则

**永远可见的原始 token 必须是常数大小。** 设 assistant 输出占轨迹的 15%，1M 时永久保留它们就有约 15 万个永远可见的原始 token，每生成一个 token 要多读约 8 GB，是 #10 设计中整个 decode 步骤（0.3–0.5 GB）的约 20 倍。所以永远可见的部分只有两段：system 和工具定义，长度固定，永久保留原文；以及一个滑动窗口，覆盖最近 2 轮、最多 8K token，超出上限时从最旧的那头开始压缩。assistant 输出和工具结果离开窗口后都会被压缩。永久保留 assistant 输出、只按轮数开窗口这两种做法都没有选，因为它们的代价随轨迹长度或单轮大小无上限地增长。

**窗口只控制可见性，不影响插入。** gist 照常按流式规则插入；一段内容离开窗口之后，改由已经存在的 summary 代表它。所以窗口是 mask 上的规则，和插入规则、树的形状无关。

**片段边界由一个标签数组给出。** 构造输入时，chat template 渲染的同时生成一个与 token 等长的片段标签（system、工具定义、assistant、工具结果），插入器、mask 特征和 kernel 都读这个数组。在 token 序列里解析模板的角色标记没有选：它依赖具体模板，换模型就要重写，而且会被内容里出现的相同字符串误导。

**流式插入跨片段连续进行。** 一段工具结果在 chunk 中间结束时，未满 4 个的 chunk 保持打开，由下一段可压缩的内容填满，chunk 可以横跨两段内容。这样树始终是规整的 4 叉，kernel 里"节点 i 的子节点是 4i…4i+3"的连续布局成立，流式插入的前缀稳定性也保留。在每段结束时关闭 chunk 没有选：叶子大小不一，上层的连续布局要重新设计，而一个 chunk 只有 4 个 token，横跨两段的语义代价很小。

**训练和推理用同一套压缩规则。** 以上每条规则都同时进入阶段一的 flex mask、推理的 mask 和 kernel。只要两边不一致，模型推理时看到的注意力模式就是训练时没见过的。

## 树的形状

**固定 L = 4 级 summary。** 第 l 级的节点覆盖 4^(l+1) 个原始 token，L = 4 时顶层节点覆盖 256 个，1M 的上下文约有 4096 个顶层节点，正好是顶层的上限，128K 时约 512 个。每一级有自己的 gist embedding 和 β 参数，训练时的层数决定了推理时最多能用几层；随长度动态加层会让推理遇到训练时没见过的层级。超过 1M 时另训 L = 5 的模型。

**分叉数和 head dim 是 kernel 的模板参数。** 现在只实例化 4 叉，以及 head dim 64（0.5B）和 128（7B）。#14 的第二轮要比较 8 叉和 16 叉，做成模板参数之后不用重写 kernel。

## 推理

**在已有缓存上追加 prefill 是一等公民。** 这是 agent 场景的主要负载：缓存跨轮保留，追加内容时按流式规则继续插 gist，已有的 summary 和选择缓存都复用。现有代码假设一次 prefill、然后一直 decode，这一点要先改。

**追加的 token 只读 summary，不做展开。** 这与现在 prefix 的处理一致，也与阶段一训练时的 mask 一致。代价是工具结果里的 token 只能通过 summary 读更早的上下文，它们的 KV 质量会略差，在质量测试阶段量化。让追加的每个 token 都像 decode 一样做 selective unfolding 没有选：每个 token 都要做一次选择，prefill 会慢得多，和训练的不一致也更大。prefill 是否也要展开由 ADR 0002 的把关实验回答。

**选择规则是逐级 beam，各种变体做成开关。** 顶层最多 4096 个节点全部打分，之后每级保留固定的 k 个（例如 256）；打分为 q·k + β，分数相同时按节点 id 打破平局。组内合并方式（每个 head 各选再取并集，或 RecSA 的组内 sum-exp）和是否把未选中的节点作为粗粒度项留在 softmax 里，参考实现和 kernel 都支持，默认"取并集、不开粗粒度项"，由 #14 的结果决定最终默认值。粗粒度项打开时采用精确划分（选中的节点只看子节点，见 ADR 0002）。现有规则（第 0、1 级选 ⌊k_len/448⌋ + 1 个、更高层选 3 个、每级最多保留 1/4）不随长度封顶，到 1M 时每个 token 约读 9 GB。

**新规则作为新的 `DECODE_SELECT` 模式，与旧路径并存。** 旧的两级路径和 `check_correctness.sh` 保留不动，它们是对照已发布 SSA checkpoint 的唯一基准。现有的 `eager_attention_forward_*` 函数体保持逐字节不变，新逻辑写成新函数；`gist_qwen2.py` 和 `gist_llama.py` 的共享逻辑保持同步。

**两个 kernel：kernel A 负责逐级选择，kernel B 负责读原文算 attention。** kernel A 对每个 KV 组流式读入候选的 K，算 q·k + β，组内合并后用 rank-select 选出前 k 个，不排序，分数不写回显存；子节点区间直接交给下一级。kernel B 按块 id 读原始 K/V，做 split-K flash-decode，最后与 sink、可见窗口和粗粒度项按 log-sum-exp 合并。

**kernel 的正确性标准是"非平局部分相同"。** 选出的集合中，分数差距大于 ε 的部分必须与 PyTorch 参考实现完全相同，差距小于 ε 的节点可以互换，但测试要证明它们确实是平局；attention 输出要求 allclose。逐位一致没有选：kernel 与参考实现的累加顺序不同，逐位一致会把两者的实现细节绑死，而 OPSD 的正确性本来不依赖它（见下文 rollout 的决定）。

**研究用的 HF 引擎，第一版 batch 1，接口按以后接 SGLang/vLLM 设计。** 训练和测量需要能改到每个细节，HF 引擎最灵活。接口提前考虑分页 KV 和请求级缓存。batch > 1 在第二步合入旧分支 `experiment/gist-hot-buffer` 的实现。

**1M 时全部放在 GPU 上，第一版不做原始 KV 下放。** 7B、1M、batch 1 在 H200 上约需 92 GB（模型 15 GB、原始 KV 约 57 GB、summary 的 KV 约 20 GB），H200 有 141 GB。#10 原设计里的主机内存下放、热缓存和预取是按 H100 的 80 GB 估算的，推迟到需要 batch > 1 或更大的模型时再做。

## 训练

**训练先用单卡。** 7B 的阶段一在 128K 上估算可以放进单张 H200。先实测显存和速度，放不下或太慢再引入序列并行；在功能还没跑通的阶段，分布式会让每个环节都更难调试。

**7B 的阶段一先用 32K 序列，再检查泛化。** L = 4 时 32K 的序列有约 128 个顶层节点，足够训练顶层路由。训练后在 128K 和 256K 上测召回和 KL；泛化不了再加长训练序列。按 0.5B 的实测（16K、L = 5 每步 65 秒），7B 在 128K 上每步会慢一两个数量级，所以"32K 能否泛化"本身是要回答的问题。

**OPSD 做单轮 on-policy，不执行工具。** 从轨迹里截取前缀，学生只生成下一轮 assistant 的输出（包括工具调用），老师打分。它在单轮之内已经是 on-policy 的；真正执行工具的多轮 rollout 需要沙箱环境，成本高一个量级，等单轮有效、且跨轮误差累积成为主要问题时再做。

**rollout 走正式推理的 kernel 路径，replay 按记录的节点 id 重算。** rollout 记录每步、每层、每个 KV 组选中的节点 id；replay 用可求导的参考实现照这些 id 构造可见集合。这样训练时的选择与推理完全相同，rollout 的速度也够用；replay 不重新做选择，所以不要求 kernel 与参考实现逐位一致。记录的是节点 id 而不是稠密 mask，因为长上下文下稠密 mask 放不下。选择不再只靠路由 KL：粗粒度项打开时，没选中的兄弟节点进入 replay 的 softmax，直接收到反向 KL 的梯度（ADR 0002）。

**OPSD 只在 128K 以内训练，另用少量 256K 样本验证泛化。** 老师需要全注意力打分，每个样本都在完整长度上算代价太高。先确认 128K 以内训练有效，再看泛化，不行再考虑更长的老师。

## 数据

**第一版用 nebius/SWE-rebench-openhands-trajectories。** 它有 6.7 万条轨迹，CC-BY-4.0，消息结构是 OpenAI 风格的 `tool_calls` 加 `tools`，最接近 Qwen2.5 的工具调用格式。它由 Qwen3-Coder-480B 生成，不是我们的老师：阶段一只把它当长文本用，影响不大；OPSD 的 prompt 分布偏离老师，由后面老师自己生成的轨迹补上。使用前抽查工具结果是否被 OpenHands 截断。

**超过 128K 的长度用拼接的轨迹，只做评测和泛化检查。** 把同一仓库或同类任务的多条轨迹首尾相接。拼接出来的长轨迹段间依赖弱，测不出真正的长程依赖，但足以检验 infra 和测召回。让老师在长周期任务上真正跑到 1M，等纵向链路打通后再考虑。

## 做法

**先打通一条纵向的最小链路，再扩展。** 第一步用 0.5B 在 128K 上从头到尾跑通：受保护片段与可见窗口 → 追加 prefill → 新选择规则的参考实现 → kernel A 与 kernel B → 阶段一 → OPSD。第二步加长到 256K 并换成 7B。原始 KV 下放、batch > 1 和 CUDA graph 放到最后。所有功能做完之后才进入质量测试（#14、长上下文 OPSD、任务评测）。按组件逐个做完没有选：组件之间的接口问题，例如 rollout 记录的节点 id 能否被 replay 正确使用，只有在端到端的链路里才检验得到。

## 后果

现有两级 SSA 的推理和 `check_correctness.sh` 不受影响。阶段一的 mask、推理的 mask、插入器和 kernel 都要认识片段标签和可见窗口，这四处必须一起改、一起测。kernel 的工作量集中在 kernel A 的 rank-select 和 kernel B 的块索引读取上。质量上有三个已知的风险，都留到质量测试阶段量化：追加的 token 只读 summary 带来的 KV 质量损失，32K 训练能否泛化到 256K，以及深层树逐级召回的累积衰减（#14）。
